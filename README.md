# GXPAI Engine

의약품 공장(GMP 시설)의 설계 도면을 읽어서 방, 기압, 장비 정보를 구조화하고, 규정 위반을
자동으로 검사하며, 나중에는 규정을 지키는 배치안까지 생성하는 엔진이다.

GMP는 의약품을 안전하게 만들기 위한 제조, 품질관리 기준이다. 이런 공장은 방마다 공기 청정도와
기압, 동선 규정이 까다로워서 지금은 사람이 도면을 일일이 검토한다. 이 프로젝트는 그 검토를
자동화하고, 한 공장이 아니라 여러 공장에 그대로 쓸 수 있게 만드는 것이 목표다.

핵심 설계 원칙: 새 공장 도면이 와도 코드는 고치지 않고 설정 파일(프로파일)만 추가해서 처리한다.
프로파일은 "이 공장 도면을 어떻게 읽어야 하는지" 적어둔 시설별 설정서다.

## 단계

1. 읽기(Ingestion) - 도면에서 방, 기압, 장비를 뽑아 데이터로 저장
2. 검사(Compliance) - 규정 위반을 찾아 리포트로 출력 (이번 계약의 핵심 납품물)
3. 생성(Generation) - 요구조건을 주면 규정을 지키는 배치안을 자동 생성
4. 지능화(Intelligence) - 요구서 문서를 AI가 읽어 입력으로 변환, 수정이력 학습
5. 서비스(Service) - 위 기능을 웹 API로 제공 (2단계 사업)

## 현재 상태

**1단계(읽기)와 2단계(검사)가 동작한다.**

실제 공장 도면에서 방 111개(3층 51, 4층 60), 장비 418개, 공조기(AHU) 20개를 추출해
저장한다. 레이어 이름과 방 번호 체계가 전혀 다른 합성 도면도 코드 수정 없이 처리된다.

검사(`validate`)는 규칙 14종 중 **LBL 3종**이 돌아 실도면에서 **위반 22건**을 찾는다:

| 규칙 | 잡은 것 |
|---|---|
| LBL-001 (3건) | 평면도와 차압도의 **방 이름이 다르다** |
| LBL-002 (17건) | 한쪽 도면에만 있는 방 |
| LBL-003 (2건) | **같은 방번호가 서로 다른 두 방에** 붙어 있다 |

나머지 11종(PRES, ADJ, HVAC)은 **일부러 잠가 뒀다**(`review: unreviewed`).
법규 해석이 걸린 규칙이라 컨설턴트 검수 전에는 돌리지 않는다 —
틀린 규칙이 위반 이력을 오염시키면 되돌릴 수 없다.
무엇이 잡힐지는 `scripts/1_운영/preview_rules.py` 로 **DB 를 건드리지 않고** 미리 볼 수 있다.

자세한 진척은 [docs/01_진행상황.md](docs/01_진행상황.md).

## 생성 단계의 실현 가능성 (연구 근거)

3단계(요구조건을 주면 규정을 지키는 배치를 자동 생성)는 막연한 목표가 아니다. 최근 논문들이
핵심 기법의 작동을 이미 보여줬고, 우리 계획은 그 결과 위에 선다.

- 규칙을 보상으로 쓰는 학습이 실제로 통한다. Mila 연구소의 floor-plan RLVR 논문(2026)은
  대형 언어모델(LLM)을 "규칙을 지키면 점수, 어기면 0점"으로 훈련해서 방 연결 관계와 면적 조건을
  동시에 만족하는 도면을 만들었고, 사람 평가에서 실제 도면과 구분되지 않는 수준의 결과를 냈다.
  여기서 "규칙 채점기"가 곧 우리가 2단계에서 만드는 위반 검사 엔진에 해당한다.
  <br>
  <br>
- 제약을 만족하는 배치를 푸는 것은 이미 빠르게 되는 문제다. 시설 배치를 다룬 CDCL/CP-SAT 비교
  논문(2026)은 인접 요구, 분리 금지 같은 제약을 밀리초 단위로 풀고, 빠른 탐색으로 찾은 초기 해를
  최적화기에 넘겨 최적해에 도달함을 보였다. 우리가 쓰기로 한 OR-Tools(CP-SAT)가 그 도구다.
  <br>
  <br>
- 규제가 심한 의료 시설에서도 요구조건에서 배치까지 한 흐름으로 동작한다. MedBuild AI(2025)는
  대화로 받은 요구를 결정론적 계산기로 정리하고, LLM이 검증된 배치 유형 안에서만 안을 만드는
  방식으로 병원 배치를 생성한다. 병원은 오염 관리와 동선 규정이 GMP와 닮은 자매 도메인이다.
  <br>
  <br>
- 기존동을 두고 증축부만 채우는 문제도 다뤄졌다. FloorplanMAE(2025)는 도면 일부를 가리고
  나머지로 전체를 복원하는데, 이번 대상이 정확히 증축(기존은 유지, 증축부만 신규)이라 맞는다.

정직한 한계: GMP 청정실 도면 생성을 직접 다룬 논문은 (2026년 기준) 없다. 부족한 것은 방법이
아니라 데이터라서, 우리는 검증된 배치를 대량으로 합성해 학습 데이터를 만드는 방식으로 이 공백을
메운다. 또한 위 논문들 모두 산출물은 "검토가 필요한 초안"이지 그 자체로 인증된 설계가 아니라고
분명히 한다.

우리 접근: 하나의 생성기를 믿지 않고, 여러 생성기(제약 풀이, 과거 사례 변형, LLM)가 후보를 내면
위반 검사 엔진이 심판을 보고, 어긋난 후보는 그 부분만 다시 풀어 고친다. LLM은 "어느 방을 어느
구역에" 같은 판단만 맡고 정확한 좌표는 제약 풀이가 계산한다(논문들이 공통으로 지적한, LLM이
좌표 계산에 약한 문제를 피하기 위함). 그래서 지금 2단계 검사 엔진을 튼튼히 만드는 것이 곧 생성의
기초공사다. 상세는 [docs/40_생성_전략.md](docs/40_생성_전략.md),
[docs/41_생성_레드팀.md](docs/41_생성_레드팀.md).

## 동작 방식

```
도면(zip/DXF) --> 읽기 --> PostgreSQL(표 형태 저장) --+
                                                     +--> Neo4j(관계 저장) --> 검사 --> 위반 리포트
   프로파일(시설별 설정) --------------------------+                        --> 생성 --> 새 도면(DXF)
```

- DXF: CAD 도면을 다른 프로그램도 읽을 수 있게 풀어쓴 파일 형식. 원본 DWG(AutoCAD 전용)는 DXF로 변환해서 쓴다.
- PostgreSQL: 정보를 표(행, 열) 형태로 저장하는 데이터베이스. 방, 도면 목록을 담는다.
- Neo4j: 정보를 관계(A방이 B방과 붙어있다, 기압이 A에서 B로 흐른다) 형태로 저장하는 데이터베이스.
- 규칙과 프로파일은 코드가 아니라 데이터(`rules/`, `profiles/`)라서, 파일만 추가하면 새 규칙, 새 시설에 대응한다.

설계 전반은 [docs/02_개발_가이드라인.md](docs/02_개발_가이드라인.md) 참고.

## 개발 환경

```bash
# 1. 데이터베이스 기동 (Docker 필요)
cp .env.example .env
docker compose up -d          # PostgreSQL + Neo4j

# 2. 엔진 설치 (Python 3.11+)
python -m venv .venv
. .venv/Scripts/activate       # macOS/Linux: source .venv/bin/activate
pip install -e ".[dev]"

# 3. 확인
gxpai --help
pytest
```

## 명령어

```bash
gxpai facility add <폴더또는zip> --name "공장이름" --profile osd_hs_2025
gxpai inventory <시설ID>        # 도면 속 레이어, 글자, 블록 통계
gxpai profile wizard <시설ID>   # 도면을 훑어 프로파일 초안 자동 생성
gxpai ingest <시설ID>           # 방, 장비, 기압을 추출해 저장
```

`facility add`, `inventory`, `profile wizard`, `ingest`, **`validate`(검사)**,
**`report`(리포트)** 는 현재 동작한다. `generate`(생성)는 3단계에서 구현할 예정이다.

예전 README 는 "validate, report 는 구현할 예정"이라고 적어 뒀는데 **틀린 서술이었다.**
  둘 다 이미 돌고 있었다. 문서가 코드보다 뒤처져 있었다.

## 저장소 규칙

- 고객 원본 도면은 커밋하지 않는다. `raw/`, `artifacts/`, `out/`, `*.dxf`, `*.dwg`, `*.zip`은
  `.gitignore`로 차단하고, 공개용 예제는 합성(가짜) 도면만 쓴다.
  검수용 렌더 이미지도 **발주처 도면을 그린 것**이므로 커밋 금지다.
  (실제로 `out/*.png` 9장이 커밋돼 있었다. `artifacts/` 는 막아 뒀는데 `out/` 을 빠뜨렸다.
   2026-07-14에 추적을 끊고 렌더 스크립트를 `artifacts/` 로 돌렸다.)
- 입력 도면은 수정하지 않는다. 모든 산출물은 다시 생성할 수 있는 파생물이다.
- 산출물에는 코드 버전, 프로파일 버전, 원본 지문(파일 내용으로 계산한 고유값, 위, 변조 확인용)을
  기록해서, 같은 입력이면 항상 같은 결과가 나오게 한다.
- 데이터베이스 구조 변경은 마이그레이션 파일(`db/migrations/NNN_*.sql`)로만 한다.

## 폴더 구조

```
gxpai/                엔진 코드
  ingest/               도면 읽기 (추출기, 블록 재귀, 텍스트 정규화)
  geometry/             방 경계, 인접, 차압 화살표 귀속
  compliance/           규칙 엔진 + 규칙별 검사 (checks/)
  core/                 파이프라인, DB, 등급 구역
  render/               리포트, SVG

profiles/             설계사무소별 설정 (레이어명, 방번호 패턴)
rules/                규정 위반 검사 규칙 (YAML, 근거조항 포함)
db/migrations/        DB 구조 정의 (NNN_*.sql 순서대로)
tests/                시험 250개 + 합성 예제 도면
legacy/               초기 프로토타입 (참고용)

docs/                 문서. 번호가 곧 읽는 순서다 → docs/README.md
  00~02                 마스터플랜, 진행상황, 가이드라인
  10번대                지금 무엇을 아는가 (데이터 분석, 한계, 검증 기록)
  20번대                발주처에 물을 것
  30번대                어떻게 만드는가 (규칙, 온보딩, 리스크)
  40번대                앞으로 (생성 단계)
  90번대                작업 기록

scripts/              번호가 곧 쓰임새다 → scripts/README.md
  1_운영                 계속 쓰는 도구 (onboard, preview_rules, audit_all)
  2_시트전처리           한 DXF 에 겹친 시트 잘라내기
  3_교차검증             화살표 vs 절대압력 대조
  4_검수렌더             눈으로 확인 (출력은 artifacts/)
  5_도면조사             1회성 조사 26개 (probe_*, diag_*)
  6_파라미터실험         값을 실측으로 정할 때 쓴 것 (try_*, tune_*)

raw/                  발주처 원본 도면. 커밋 금지
artifacts/            산출물, 렌더 이미지. 커밋 금지
```
